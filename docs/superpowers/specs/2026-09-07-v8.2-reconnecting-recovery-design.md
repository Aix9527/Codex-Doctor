# Codex Doctor V8.2.0 — Reconnecting 端到端自愈设计

日期：2026-09-07  
状态：DESIGN APPROVED  
目标分支：`feature/v8.2-reconnecting-recovery`

## 1. 目标

V8.2.0 在 V8.1.2 原生维修中心基础上新增一个专门面向 **Codex / ChatGPT Desktop 一直 Reconnecting** 的闭环自愈流程。

V8.2.0 不把“进程已重新启动”当作连接恢复成功。完整成功必须满足：

1. 修复前完成可审计快照；
2. 自动选择可验证的网络路径；
3. 仅执行安全白名单修复；
4. 需要时重启扫描确认的 Desktop；
5. 修复后重新执行网络诊断；
6. 新网络诊断必须证明存在可用 Codex 网络路径；
7. Desktop 重启后必须重新 discovery，确认目标客户端仍存在且正在运行；
8. 只有网络与 Desktop 双重验证通过才返回 `RECOVERED`。

## 2. 主界面

扫描完成后在现有按钮组中新增：

```text
[ Reconnecting 自愈 ]
```

按钮只在全量扫描已经完成且不存在阻止自动动作的 Critical/ManualRequired 安全门时启用。

用户点击后显示分阶段进度：

```text
建立修复前快照
→ 选择网络路径
→ 应用安全修复
→ 重启 Desktop（如需要）
→ 重新诊断
→ 重新发现 Desktop
→ 生成恢复结论
```

## 3. ReconnectingRecoveryService

新增独立服务 `ReconnectingRecoveryService`，负责流程编排，不直接承担底层代理扫描、文件写入或进程控制实现。

### 3.1 输入

服务消费：

- `CodexHealthScanResult beforeScan`
- 最新 `CodexDiscoveryResult`
- 最新 `DiagnosisResult`
- 已有 `RepairService` / RepairPlan 安全动作
- 已确认 Desktop EXE/PID

### 3.2 输出

新增：

```csharp
public enum ReconnectingRecoveryStatus
{
    Recovered,
    NetworkRecovered,
    ProxyFailed,
    DnsFailed,
    TlsFailed,
    DesktopRestartFailed,
    ManualRequired
}
```

以及：

```csharp
public sealed record ReconnectingRecoveryResult(
    ReconnectingRecoveryStatus Status,
    string SummaryZh,
    Guid BeforeScanId,
    Guid? AfterScanId,
    string? SelectedProxyUrl,
    bool NetworkVerified,
    bool DesktopVerified,
    IReadOnlyList<RepairActionResult> Actions);
```

## 4. 网络路径决策

V8.2.0 必须复用现有 DiagnosisService 的事实，不新增未经验证的代理猜测。

决策顺序固定为：

1. **直连可用**：直接 TLS/网络路径已经健康时，不写 `.codex/.env`，避免不必要代理依赖。
2. **直连不可用，但本地代理已通过 HTTPS 验证**：选择 `DiagnosisResult.ProxyUrl` 作为 Codex 专用代理候选。
3. **当前 `.codex/.env` 缺失或 HTTP/HTTPS 不一致**：执行现有 `codex.proxy.env` 白名单动作。
4. **Git/npm 代理与已验证路径冲突**：仅执行现有 Git/npm 白名单清理动作。
5. **没有任何可验证网络路径**：不修改配置，按 DNS/TLS/Proxy 事实返回失败或 `ManualRequired`。

禁止：

- 只根据“常见端口”写入代理；
- 写入未经 HTTPS 验证的代理 URL；
- 在直连已经健康时强制代理；
- 修改系统级代理作为默认自愈动作。

## 5. `.codex/.env` 修复

继续复用 V8.1.x 的安全原则：

- 保留无关环境变量；
- 修改前创建备份；
- 仅写入经过验证的 `HTTP_PROXY` / `HTTPS_PROXY`；
- 两者必须使用同一个已验证 URL；
- 写入后重新读取验证；
- 验证失败自动回滚；
- 不默认写 Windows 用户级 HTTP/HTTPS 代理环境变量。

## 6. Desktop 重启与验证

如果修复动作改变了 Codex 专用代理配置，或 Desktop 当前处于运行状态，则使用扫描确认的真实 EXE/PID 执行重启。

重启成功不能只依赖 `Process.Start` 或 PID 存在。

修复后必须：

1. 重新执行 `CodexDiscoveryService.ScanAsync()`；
2. 确认与修复前同一真实 EXE 路径的 Desktop 仍被发现；
3. 确认该客户端至少一个实例处于运行状态；
4. 再执行完整 `CodexHealthScanner.ScanAsync()`；
5. 使用该新扫描中的网络诊断事实判定网络是否恢复。

如果网络已恢复但 Desktop 未验证，返回 `NETWORK_RECOVERED`；不得返回 `RECOVERED`。

## 7. 状态映射

### `RECOVERED`

- 修复后网络路径已验证；
- Desktop 已重新 discovery 且正在运行；
- 没有阻断性 Reconnecting 网络问题。

### `NETWORK_RECOVERED`

- 修复后网络已恢复；
- Desktop 重启/运行验证失败或仍不确定。

### `PROXY_FAILED`

- 代理候选存在但 HTTPS 验证失败，或代理配置写入后验证失败且已经回滚。

### `DNS_FAILED`

- DNS 诊断失败且没有其它已验证路径可绕过。

### `TLS_FAILED`

- DNS 正常，但直接 TLS 失败，且没有可验证代理路径。

### `DESKTOP_RESTART_FAILED`

- 网络路径已恢复，但扫描确认的 Desktop 无法成功重启/重新发现。

### `MANUAL_REQUIRED`

- 安全门阻止自动修复；
- 无法确定可信 Desktop；
- discovery/diagnosis 事实不足以执行安全动作；
- 需要用户完成外部步骤。

## 8. 报告

`HealthReportExporter` 增加可选 `ReconnectingRecoveryResult` 区段，至少记录：

- 修复前 ScanId；
- 修复后 ScanId；
- 最终状态；
- 网络是否验证；
- Desktop 是否验证；
- 选中的代理 URL（仅 URL，不包含认证信息；继续使用既有脱敏）；
- 每个修复动作的执行、验证、回滚结果；
- 中文失败摘要。

如果自愈失败，报告必须能区分 DNS / TLS / Proxy / Desktop Restart / ManualRequired，而不是统一写“修复失败”。

## 9. 安全边界

V8.2.0 保持以下硬门：

- Windows `requireAdministrator`；
- 扫描默认只读；
- 自动动作仅来自 RepairPlan 白名单；
- 不直接删除应用目录；
- 不修改未知数据库、MSIX/AppX 或二进制资源；
- 不下载第三方代理、安装器或脚本；
- 不调用 `powershell.exe` / `pwsh.exe`；
- 不把命令退出码、PID 存在、单次 HTTP 成功中的任一项单独作为最终恢复证明；
- 报告继续脱敏 Key/Token/Secret/Password/Cookie/Auth/Session/Bearer。
