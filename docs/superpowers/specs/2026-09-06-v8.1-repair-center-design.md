# Codex Doctor V8.1 — 一键扫描与智能维修中心设计规格

日期：2026-09-06  
状态：DESIGN APPROVED / SPEC REVIEW PENDING  
目标分支：`feature/v8.1-repair-center`

## 1. 背景

V8.0.1 已具备原生 WinForms、网络诊断、本机 Codex Desktop / CLI 扫描、真实路径重启、`.codex` 审计、迁移/恢复、中文设置与报告导出能力，但当前交互仍以多个独立按钮为中心：用户进入软件后需要自行判断先扫描、诊断还是修复，也只能得到单一 `FailureClass` 级别的总体网络结论。

V8.1 将产品形态从“工具集合”升级为“Codex 维修中心”：软件必须先以管理员权限启动，进入后先完成统一一键扫描，生成多问题健康报告与严重度分级，然后仅显示与当前状态相关的主操作。所有可安全、确定、可验证修复的问题进入统一 Repair Engine；无法安全自动处理的问题明确标记为需人工或外部处理，禁止伪报“已修复”。

## 2. 核心目标

V8.1 的用户主路径固定为：

```text
双击 CodexDoctor.exe
        ↓
Windows UAC 请求管理员权限
        ↓
Codex Doctor 首页
        ↓
[ 一键扫描 Codex ]
        ↓
统一扫描全部支持项目
        ↓
生成问题列表与严重度
严重 / 紧急 / 警告 / 提示 / 正常
        ↓
显示智能操作区
启动 Codex / 重启 Codex / 一键修复 / 一键迁移或恢复 / 一键中文 / 导出报告
        ↓
一键修复时生成 RepairPlan + 备份 + 逐项验证
        ↓
自动复检
        ↓
展示修复前后对比并允许导出最终报告
```

## 3. 非目标与边界

“一键修复全部问题”定义为：**修复 Codex Doctor 能明确检测、拥有确定修复策略、能够安全执行并能够在执行后验证的问题。**

以下情况不得伪装成可自动修复：

- OpenAI 服务端故障或区域性服务不可用。
- 用户互联网完全中断且本机不存在可用替代链路。
- ChatGPT / Codex 账号状态、订阅、服务端权限或风控问题。
- Windows 本身损坏、第三方杀毒软件阻断、企业策略阻止等无法在 Codex Doctor 内确定修复的问题。
- 未知版本的 Codex / ChatGPT Desktop 内部数据库或签名后的 MSIX/AppX 资源。
- 任何无法形成“检测证据 → 确定修复 → 修复后验证”的问题。

这类问题必须进入 `ManualRequired` / `ExternalRequired` 状态，并向用户说明原因和下一步，而不是显示“修复成功”。

## 4. 强制管理员启动

### 4.1 行为

正式 EXE 必须携带 Windows application manifest：

```xml
<requestedExecutionLevel level="requireAdministrator" uiAccess="false" />
```

因此：

1. 用户双击 EXE 时先由 Windows 弹出 UAC。
2. 用户批准后才进入主界面。
3. 用户拒绝 UAC 时应用不进入主界面。
4. 不允许通过启动后再调用 PowerShell、`runas` 脚本或第二个辅助 EXE 提权。

### 4.2 运行时校验

即便有 manifest，程序仍需在启动阶段读取当前 Windows 身份并确认管理员角色。若由于异常部署导致未处于管理员上下文，则只显示明确错误并退出，不进入维修中心。

主界面顶部显示：

```text
运行权限：管理员 ✓
系统：Windows 10/11 x64
Codex 状态：待扫描 / 已扫描
```

## 5. 首次进入界面

### 5.1 扫描前状态

首次进入主界面时不再展示十多个并列功能按钮。

主操作区域只保留：

```text
Codex Doctor V8.1

在开始之前，请先扫描本机 Codex。

[ 一键扫描 Codex ]

将检查 Codex 安装、配置、网络、代理、运行环境、.codex、CLI、迁移状态与语言状态。
```

高级工具与维修动作在首次扫描完成前隐藏或禁用。

### 5.2 扫描中状态

扫描过程中显示当前阶段而不是冻结界面，例如：

```text
正在扫描 7 / 12
✓ 管理员权限
✓ Codex Desktop
✓ Codex CLI
→ 网络与 TLS
○ 代理
○ .codex
...
```

扫描必须异步执行；GUI 不能因 DNS、TLS、代理或外部命令调用而无响应。

## 6. 统一扫描架构

新增统一编排层 `CodexHealthScanner`，复用但不直接暴露现有 `DiagnosisService`、`CodexDiscoveryService`、`MigrationService`、`CodexLanguageService` 的内部细节。

### 6.1 扫描范围

统一扫描至少覆盖：

1. 管理员权限与系统平台。
2. Codex Desktop / ChatGPT Desktop 安装、真实 EXE、版本、安装来源。
3. Desktop 运行进程、PID 与是否可启动。
4. Codex CLI 是否存在、真实入口、版本、PATH 可调用状态。
5. `%USERPROFILE%\.codex` 是否存在。
6. `.codex` 是否为普通目录、Junction / Reparse Point、目标路径是否有效。
7. 最近迁移状态是否完整、是否存在中断/残留状态。
8. `.codex/.env` 与 `config.toml` 等已知文本配置。
9. HTTP_PROXY / HTTPS_PROXY / ALL_PROXY / NO_PROXY 及大小写变体的一致性。
10. Windows 用户环境代理变量。
11. Windows 系统代理。
12. Git 全局代理。
13. npm 代理。
14. DNS（OpenAI / ChatGPT 域名）。
15. 直接 TLS。
16. 已发现代理的真实 HTTPS 可用性。
17. Clash Verge / Mihomo / sing-box 等相关进程。
18. TUN 网卡状态。
19. 当前 Codex Desktop / CLI 网络路径是否具备可用方案。
20. 中文 UI 状态及可信适配器能力。
21. 配置文件权限与可写性（仅针对 Codex Doctor 需要维护的已知文件）。
22. 支持的启动 / 重启路径是否有效。

### 6.2 扫描原则

- 扫描默认只读。
- 扫描阶段不修改注册表、不改 PATH、不删除文件、不写配置。
- 读取配置时继续执行敏感值脱敏。
- 每一检查项必须产生独立结果，不能只生成一个总 `FailureClass`。
- 单个检查异常不得导致整个扫描中止；扫描器收集该项异常后继续执行其余可执行检查。
- 对具有依赖关系的检查允许明确跳过，例如 DNS 完全失败时直接 TLS 可标记为“因 DNS 失败跳过”。

## 7. 统一问题模型

新增 `CodexIssue` 模型，至少包含：

```text
Id
Category
Severity
TitleZh
SummaryZh
EvidenceZh
ImpactZh
Status
AutoRepairable
RepairActionId
RequiresAdmin
RequiresCodexRestart
RequiresUserConfirmation
BackupRequired
VerificationId
SourceCheckId
```

### 7.1 严重度

固定五级：

- `Critical` — 严重问题：会阻止 Codex 启动、联网或读取核心配置，且当前无健康替代链路。
- `Urgent` — 紧急修复：当前可继续使用或存在替代链路，但配置错误/缺失会持续导致重连、失败或高概率故障。
- `Warning` — 警告：存在不一致或潜在风险，但当前主要功能可用。
- `Info` — 提示：非故障信息、可选优化或需要用户知情的状态。
- `Ok` — 正常：检查已通过。

### 7.2 问题状态

- `Detected`
- `Repairable`
- `Repairing`
- `Fixed`
- `RepairFailed`
- `ManualRequired`
- `ExternalRequired`
- `NotApplicable`

### 7.3 聚合摘要

扫描完成后显示：

```text
严重问题  2
紧急修复  3
普通警告  1
提示信息  2
正常项目 15
```

并按 `Critical → Urgent → Warning → Info → Ok` 排序。

## 8. 一键修复 Repair Engine

新增 `CodexRepairEngine`，禁止 MainForm 直接串联大量文件/进程修改逻辑。

### 8.1 RepairPlan

根据最新扫描结果生成不可变的 `RepairPlan`：

```text
PlanId
CreatedAt
SourceScanId
Actions[]
RequiresRestart
ManualIssues[]
ExternalIssues[]
```

每个 `RepairAction` 至少包含：

```text
ActionId
IssueId
TitleZh
Order
RiskLevel
BackupStrategy
Execute
Verify
Rollback
RequiresRestart
```

### 8.2 可进入自动修复的典型问题

在实现具备明确检测与验证的前提下，一键修复可覆盖：

- 已验证代理存在但 Codex `.env` 缺失。
- Codex HTTP/HTTPS 代理不一致。
- Codex `.env` 中失效代理可被已验证代理安全替换。
- 大小写代理变量不一致。
- `NO_PROXY` 缺失本机地址时补全。
- Git/npm 全局代理与当前 Codex 可用代理冲突，且用户已在一键修复确认页授权统一/清理。
- 可确定的已知文本配置格式问题。
- `.codex` Junction 指向不存在目标且存在确定恢复路径时修复。
- 已记录迁移事务处于可安全恢复的中间状态。
- 已知 Codex Desktop 进程需要重新加载已修复配置时重启。
- 中文 UI 存在已验证可信适配器时自动设置并保留恢复信息。

每增加一种自动修复，必须同时增加对应检测、备份、验证和回滚合同。

**Windows 用户级 `HTTP_PROXY` / `HTTPS_PROXY` 不属于默认一键修复写入范围。** V8.1 默认优先修复 Codex 专用配置，避免影响浏览器、Git、npm 或其他应用。若未来保留“同时写入 Windows 用户环境变量”的高级选项，必须由用户在高级设置中显式选择，并在 RepairPlan 中单独列为高影响动作。

### 8.3 不自动修复的典型问题

- 未知代理来源且无法通过 HTTPS 验证。
- 删除用户未知配置。
- 修改 MSIX/AppX 安装资源。
- 修改未知数据库。
- 自动安装/卸载 Codex Desktop 或 CLI。
- 自动更改用户账号、登录状态或凭据。
- 无证据地重置整个 `.codex`。
- 默认修改 Windows 用户级代理环境变量。

### 8.4 修复事务

执行流程：

```text
扫描结果
  ↓
生成 RepairPlan
  ↓
显示将修改的项目
  ↓
用户一次确认
  ↓
为每项建立备份/恢复信息
  ↓
逐项执行
  ↓
每项立即验证
  ├─ 成功 → 标记 Fixed
  └─ 失败 → 执行该项 Rollback → 标记 RepairFailed
  ↓
需要时重启 Codex
  ↓
全量重新扫描
  ↓
生成修复前/修复后对比
```

一个动作失败不能使后续互不依赖的动作全部丢失；有显式依赖的后续动作必须跳过并说明原因。

**取消语义固定如下：**用户可以在 RepairPlan 确认页取消，取消后不得产生任何写入；一旦用户确认并进入实际写入阶段，为避免在多步骤事务中制造新的半完成状态，V8.1 不提供“强制中途取消”按钮。若程序自身发生异常，则按照当前动作的 Rollback 规则恢复，并继续生成可审计结果。

## 9. 一键修复 UI

扫描完成且存在 `AutoRepairable=true` 的问题时显示主按钮：

```text
[ 一键修复全部可自动修复问题 ]
严重 2 · 紧急 3 · 共可修复 5 项
```

点击后先显示简洁确认页：

```text
将自动修复 5 项：
✓ Codex HTTPS_PROXY
✓ .env 代理一致性
✓ Git 代理冲突
✓ npm 代理冲突
✓ 重启 Codex 重新加载配置

不会自动处理：
- OpenAI 服务端状态（外部问题）

[开始修复] [取消]
```

执行中显示实时进度。完成后必须自动复检，不能仅根据“写文件成功”宣告问题已解决。

如果没有任何可自动修复问题，按钮显示健康状态或“没有可自动修复项”，不得执行无意义写入。

## 10. 扫描完成后的主操作区

首次扫描完成后首页显示六个核心操作：

```text
[ 启动 Codex ]     [ 重启 Codex ]

[        一键修复全部可自动修复问题        ]

[ 一键迁移/恢复 Codex ]

[ 一键设置 Codex 简体中文 ]

[            导出完整报告            ]
```

其余功能进入“高级工具”：

- 运行 `codex doctor`
- Git/npm 详细代理管理
- 代理明细
- 配置文件审计
- CLI 信息
- 安装路径
- 原始扫描明细

## 11. 启动 / 重启 Codex

### 11.1 启动 Codex

新增 `StartCodexDesktop`，只使用扫描确认的 Desktop 实际可执行路径或受支持的已解析启动目标。

- 未发现 Desktop：按钮禁用并说明原因。
- 已发现且未运行：显示“启动 Codex”。
- 已运行：可显示“打开 Codex”或保持“启动”禁用。

### 11.2 重启 Codex

继续使用扫描到的真实 EXE + PID，不依赖 `chatgpt:` URL scheme。

重启前必须确认已选择正确 Desktop 实例；若发现多个安装，优先当前运行实例并在详情中保留选择能力。

## 12. 智能迁移 / 恢复按钮

不再并列展示“迁移 .codex”和“恢复 .codex”。根据扫描结果自动决定按钮语义：

```text
普通 .codex 且无有效迁移状态
→ 一键迁移 Codex

.codex 为有效 Junction
→ 恢复 Codex

检测到可恢复的中断迁移
→ 修复迁移状态

状态不明确
→ 查看迁移详情（禁止自动改动）
```

迁移仍必须遵循现有安全边界：目标非空不得覆盖、保留原数据、验证 Junction、保留可恢复状态。

如果当前没有历史迁移目标，点击“一键迁移 Codex”时必须先显示目标确认界面；默认建议值可以是 `D:\Codex`，但不得静默迁移。若已存在上次成功/未完成事务记录，则优先展示该目标并要求用户确认。

## 13. 一键设置简体中文

V8.0.1 的安全边界继续保持：

- UI 语言、回答语言偏好、CLI 输出偏好继续区分。
- 只有明确验证并加入白名单的 Desktop UI 本地语言适配器才允许自动写 `zh-CN`。
- 普通 `.codex/.env` / `config.toml` 中同名 `language` / `locale` / `ui_language` 不能被冒充为 Desktop UI 设置。
- 没有可信适配器时显示“需要用户操作”，提供官方客户端设置引导，不伪报成功。
- 不修改签名后的 MSIX/AppX 资源或二进制文件。

扫描完成后按钮状态应反映：已是中文 / 可自动设置 / 需要用户操作。

## 14. 导出完整报告

“导出完整报告”属于首页主按钮，扫描完成后始终可见。

### 14.1 报告内容

报告至少包含：

- V8.1 版本与生成时间。
- 管理员权限状态与 Windows 基本信息。
- ScanId。
- Codex Desktop / CLI 安装、版本、路径、运行状态。
- `.codex`、Junction、迁移状态。
- 网络、DNS、TLS、代理、TUN。
- Windows / Git / npm 相关配置。
- 配置审计结果。
- 中文设置能力与当前状态。
- 全部问题及严重度。
- 自动修复能力。
- 若执行过修复：RepairPlan、每项执行结果、回滚结果、修复前后对比。
- 仍未解决的问题与 ManualRequired / ExternalRequired 原因。

### 14.2 格式

首选继续提供 UTF-8 中文 JSON，结构升级为 `CodexHealthReportV81`。

文件名示例：

```text
CodexDoctor-V8.1-Report-20260906-180000.json
```

### 14.3 脱敏与路径隐私

以下键或等价敏感字段不得输出真实值：

- TOKEN
- API_KEY / KEY
- SECRET
- PASSWORD
- COOKIE
- AUTH
- SESSION
- 登录凭据

报告只允许显示“已配置 / 未配置”或脱敏后的非秘密元数据。

为便于用户把报告直接发送给他人排障，所有位于用户主目录下的路径在导出报告中统一规范化，例如：

```text
C:\Users\Alice\.codex\config.toml
→ %USERPROFILE%\.codex\config.toml
```

GUI 本机显示可以使用真实路径，但导出报告默认不暴露 Windows 用户名。

## 15. 首页状态与按钮显隐规则

主界面采用状态驱动，而不是“所有按钮永远可点”。

示例：

```text
未扫描
→ 只突出显示“一键扫描 Codex”

Codex 未安装/未发现
→ 禁用启动、重启；显示相关问题

Codex 已安装但未运行
→ 启用“启动 Codex”

Codex 正在运行
→ 启用“重启 Codex”

存在可修复问题
→ 启用“一键修复”，显示可修复数量

全部关键检查通过
→ 显示“✓ Codex 状态健康”

普通 .codex
→ “一键迁移 Codex”

有效 Junction
→ “恢复 Codex”
```

## 17. 错误处理

- 每个扫描器产生自己的失败结果，不允许一个异常中断全部扫描。
- 修复动作失败必须记录原始错误的安全摘要，但正常用户弹窗使用中文可操作说明。
- 技术异常可写入报告中的脱敏诊断字段，不直接暴露秘密或完整敏感路径内容。
- 修复失败时若已修改文件，必须尝试该动作的回滚；回滚失败要提升为 `Critical` 并明确保留备份位置。
- 用户在开始写入前取消时不得留下任何修改；开始写入后不提供强制中途取消，异常按事务规则回滚。

## 20. 成功标准
